# Code Explain Expert v4.0 — 项目长期记忆

## 项目定位
- 这是用户自研的 WorkBuddy skill，路径 `D:\1\Code-Explain-Expert\Code-Explain-Expert-v4.0`。
- 功能：通读大型项目源码 → 生成 ZHIDAO.md（导航）/ README.md（门面）/ Description.md（名片）+ 批量加意图级注释。
- 核心承诺：**只加注释，绝不改逻辑；客户项目零污染；写入前必先告知用户待改清单并等确认**。

## 产物三件套定位
| 产物 | 读者 | 篇幅 | 深度 |
|---|---|---|---|
| ZHIDAO.md | 通读源码的开发者 | 300-800 行 | 为什么 + 机制 + 逐文件导读 |
| README.md | 项目访客 | 50-150 行 | 是什么 + 怎么用 |
| Description.md | 列表浏览/搜索者 | 300-350 字符 × 中英双版 | 是什么 + 含金量 + 技术栈构成 + 场景 |

## Description 写作硬规则（2026-08-18 更新）
- **含金量段必填**：必须列 2-4 个**具体技术机制**（编排亮点 / 稳定性设计 / 工程约束 / 自研组件），不可只写"是 X 系统，能做 Y"。这是 Description 区别于标签的关键。
- **结构灵活 3-4 句**：4 个维度（是什么 / 含金量 / 技术栈+工程构成 / 目标场景）可融合到 3-4 句，信息密度优先于语法完整。
- **中英不对等**：英文版可用主动语态 + 形象化隐喻（如 "turns X into Y"），可省略中文版次要细节，非逐句翻译。
- **含金量机制可追溯**：必须从 ZHIDAO.md / 源码提炼，不可编造。
- 黄金案例：`references/samples/Description/Description1.md`（Code Explain Expert 自身：含金量在工程约束）、`Description2.md`（格物：含金量在编排与稳定性）。

## 用户偏好（项目相关）
- Description 偏好"技术严谨版"（风格 C）——一眼看清仓库具体工作实现，对严肃项目/团队有说服力。
- 黄金样例是用户认可的标杆，风格把握不准时必对照 `references/samples/` 对应子目录。

## Skill 安全红线（违反即事故）
- **绝不执行 git 写操作**（commit/push/branch/checkout/reset 等任何修改 git 状态或历史的命令）。
- **绝不在客户项目目录造任何缓存/备份/中间文件**——所有中间产物落盘到 skill 目录下 `.work/`，完成后清理。
- **绝不把客户项目代码上传任何远端**。
- **备份与版本控制完全由用户自己负责**——Step 0 只告知用户待改清单 + 提醒自行备份，不替用户做备份决策。
- **回滚由用户主导**——只提示命令，绝不执行 git 回滚命令。
