# Description 写作规范——唯一权威

> 生成项目 Description 时**只读本文件**。Description 是"项目名片"（给列表展示 / 搜索结果 / 卡片预览用），比 README 更短更精炼，但必须有"含金量"——具体技术机制而非泛泛标签。**含金量段是 Description 区别于"标签"的关键，不可省**。

## 1. 三个产物的定位区别（必须分清）

| 维度 | Description.md | README.md | ZHIDAO.md |
|---|---|---|---|
| 读者 | 列表浏览者 / 搜索者 | 项目访客 | 要通读源码的开发者 |
| 篇幅 | **300-350 字符**（中英各一版） | 50-150 行 | 300-800 行 |
| 深度 | 是什么 + **含金量机制** + 技术栈构成 + 场景 | 是什么 + 怎么用 | 为什么 + 机制 + 逐文件导读 |
| 场景 | GitHub About / 卡片预览 / 简历项目描述 / 搜索摘要 | GitHub 首页 / 项目门面 | 开发者通读代码 |
| 格式 | 外层章节标题用 markdown，**描述正文纯文本** | Markdown | Markdown |

## 2. 字符数约束（硬性）

- **每版 300-350 字符**（含标点空格，不含换行与外层 markdown 标题）
- 中文版按中文字符计（1 个汉字 = 1 字符）
- 英文版按 ASCII 字符计
- **低于 300 或超过 350 必须重写**——这个区间是为 GitHub About 字段限制（350）设计的
- **信息密度优先于语法完整**：长句可承载多个维度，不必为凑句数硬切

## 3. 内容结构（3-4 句，必含"含金量"段）

| # | 维度 | 写法 | 案例（取自 `samples/Description/`） |
|---|---|---|---|
| 1 | 是什么 + 解决什么 | 一句话定义：`<项目名> 是一个 <类型>，<解决什么问题 / 解决方式>` | "格物（Gewu Deep Research）是一个基于 LangGraph 构建的开箱即用的多 Agent 深度研究系统，输入研究问题即可从需求澄清、研究简报、并行搜索、发现压缩到带引用 Markdown 报告的全流程自动化能力" |
| 2 | **含金量（核心，不可省）** | 列 **2-4 个具体技术机制**（不是泛泛功能）——编排亮点 / 稳定性设计 / 工程约束 / 自研组件。可明示"其含金量在 X："开头 | "其含金量在编排与稳定性：主管 Supervisor 子图拆解调度、多个研究员 Supervisor 子图并行搜索，Token 超限自动截断重试与异步并行检索、结构化输出自动重试、三层状态隔离与平台级 Supabase 认证鉴权" |
| 3 | 技术栈 + 工程构成 | 不只说"基于 X 构建"，要列**具体脚本/模块/语言组合/工具生态** | "工程由 extract_skeleton.py、fetch_sources.py、bigfile_split.py 三个 Python 脚本构成，约束 git 只读、缓存落盘 skill 目录、源码不出本机，兼容 Java、Python、JS、TS、Go" |
| 4 | 目标用户 + 适用场景 | 谁用 / 什么场景用，**可与句 3 融合**为一句 | "适合快速搭建或二次工程化研究型 Agent" |

**结构灵活**：3 句长句或 4 句短句均可，关键是 4 个维度都覆盖到（维度 3、4 可融合到一句）。死板凑"4 句话"反而会稀释信号密度。

## 4. 文件格式

```markdown
# Description

## 中文版

<300-350 字符中文描述，纯文本无 markdown 语法>

## English

<300-350 characters English description, plain text no markdown>
```

输出到**目标项目根目录** `Description.md`。

外层 `# Description` / `## 中文版` / `## English` 是文件结构标记，**描述正文必须是纯文本**——不用 `**`、`[]()`、`` ` `` 等语法（GitHub About 字段不渲染 markdown，正文里出现 markdown 语法会被当原文显示）。

## 5. 风格要求

1. **描述正文纯文本无 markdown**：外层章节标题有 markdown，但描述内容里不用 `**`、`[]()`、`` ` `` 等
2. **必须有含金量段**：列 2-4 个**具体技术机制**（如"Supervisor 子图拆解"、"Token 超限自动截断重试"、"git 只读约束"、"三层状态隔离"），不能只说"是一个 X 系统，能做 Y"。**含金量是 Description 区别于"标签"的关键**——读者看完含金量段应立刻知道这个项目的工程严格度 / 编排复杂度 / 稳定性设计的水平
3. **中英版不对等**：不是逐句翻译。英文版可用主动语态 + 形象化隐喻（如 "turns X into Y"），可省略中文版的次要细节，保持同等信息密度但不必字字对应。中文版偏陈述铺陈，英文版偏主动凝练
4. **术语保留英文原文**：中文版里框架名/协议名/组件名不翻译（`LangGraph`、`Supervisor`、`Supabase`、`React`、`MCP`、`Vite`）
5. **不展开实现细节**：Description 是名片不是教程，"怎么实现的"交给 ZHIDAO.md；但**机制名**（如"Supervisor 子图"、"Token 重试"、"三层状态隔离"）可点出，不展开原理
6. **一句话能说清的不用两句**：信息密度优先于语法完整

## 6. 数据来源

- **项目名 / 类型**：从 `extract_skeleton.py` 的 `project_root` + 构建标志文件推断
- **核心功能**：从 skeleton.json 的 `modules` + 入度最高的文件推断
- **含金量段（必填，最重要）**：从 ZHIDAO.md（若已生成）的"机制亮点 / 关键设计"章节，或 skeleton.json 的 `dependency_links` / 出入度高的文件提炼——必须是**源码里真实存在的机制**，不可凭空编造。若 ZHIDAO.md 未生成，必须先扫一遍核心源码（用 `fetch_sources.py` 捞出入度最高的 3-5 个文件）确认机制存在
- **技术栈 + 工程构成**：从 `language_hint` + 构建标志文件 + imports + 关键脚本/模块名推断。脚本名/模块名要列具体的（如 `extract_skeleton.py`），不要只说"基于 Python"
- **目标场景**：从 ZHIDAO.md（若已生成）的"推荐阅读路径"或 README 推断

## 7. 已有 Description.md 的处理

- **绝不覆盖**已有 Description.md（除非用户明确要求重写）
- 用户要"更新"时保留原文，只更新过时信息
- 用户没提 Description 就不动

## 8. 正反例速查（对照 `samples/Description/`）

### 正例 1（Code Explain Expert 自描述）——含金量在工程约束

> ...是一套以客户项目零污染为最高原则的 AI 代码解读流水线...**它通过写入前确认护栏、骨架提取、宏观导航、可选 README/Description 与精准注释五阶段工作**，所有注释均为非破坏性追加，写入前必先告知待改清单并等待确认。**工程由 extract_skeleton.py、fetch_sources.py、bigfile_split.py 三个 Python 脚本构成，约束 git 只读、缓存落盘 skill 目录、源码不出本机**...

✅ 含金量具体到"五阶段"、"三个脚本名"、"git 只读约束"——读者立刻知道工程严格度。
✅ 英文版用主动语态凝练："adds readable docs without ever touching your source logic"，不逐句翻译。

### 正例 2（格物）——含金量在编排与稳定性

> ...**其含金量在编排与稳定性：主管 Supervisor 子图拆解调度、多个研究员 Supervisor 子图并行搜索，Token 超限自动截断重试与异步并行检索、结构化输出自动重试、三层状态隔离与平台级 Supabase 认证鉴权**...

✅ 含金量段直接以"其含金量在 X："开头明示，列 5 个具体机制（子图拆解 / 并行搜索 / Token 重试 / 状态隔离 / Supabase 鉴权），信号密度极高。
✅ 英文版用形象化隐喻："turns a question into a cited report"——一句说清输入输出价值。

### 反例（标签堆砌，不可写）

> Code Explain Expert 是一个 AI 代码解读工具，能帮助开发者理解项目，基于 Python 构建，适合所有开发者使用。

❌ 没有含金量段，"AI 代码解读工具"是标签不是机制。
❌ "基于 Python 构建"过于泛泛（没列脚本名）。
❌ "适合所有开发者"过于宽泛（没说具体场景）。
❌ 4 句话结构齐备但信号密度为零——正好踩中"为凑 4 句而稀释"的坑。

## 9. 质量验收

- [ ] 中文版 300-350 字符
- [ ] 英文版 300-350 characters
- [ ] **含金量段存在**（至少 2 个具体技术机制，非标签）
- [ ] 4 个维度齐备（是什么 / 含金量 / 技术栈+工程构成 / 目标场景），可融合到 3-4 句
- [ ] 描述正文纯文本无 markdown 语法（外层章节标题除外）
- [ ] 中英双版不对等（英文版可更精炼，非逐句翻译）
- [ ] 含金量机制在源码 / ZHIDAO.md 中可追溯（不编造）
- [ ] 已有 Description.md 未被覆盖（除非用户要求重写）
