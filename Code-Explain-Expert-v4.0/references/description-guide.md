# Description 写作规范——唯一权威

> 生成项目 Description 时**只读本文件**。Description 是"项目名片"（给列表展示 / 搜索结果 / 卡片预览用），比 README 更短更精炼，但必须有"含金量"——具体技术机制而非泛泛标签。**含金量段是 Description 区别于"标签"的关键，不可省**。

## 1. 三个产物的定位区别（必须分清）

| 维度 | Description.md | README.md | ZHIDAO.md |
|---|---|---|---|
| 读者 | 列表浏览者 / 搜索者 | 项目访客 | 要通读源码的开发者 |
| 篇幅 | **中文版 ≤ 350 字符**（GitHub About 部署约束）；英文版不设限 | 50-150 行 | 300-800 行 |
| 深度 | 是什么 + **含金量机制** + 技术栈构成 + 场景 | 是什么 + 怎么用 | 为什么 + 机制 + 逐文件导读 |
| 场景 | GitHub About / 卡片预览 / 简历项目描述 / 搜索摘要 | GitHub 首页 / 项目门面 | 开发者通读代码 |
| 格式 | 外层章节标题用 markdown，**描述正文纯文本** | Markdown | Markdown |

## 2. 篇幅约束

字数不是写作目标，信息密度才是。**写满该写的机制，不为凑字注水，不为省字砍机制**。大模型最常见的偷懒就是把"满足字数"当成存在意义——凑出来的字数是噪音，读者一眼看穿。

- **中文版 ≤ 350 字符**（含标点空格，不含换行与外层 markdown 标题；1 个汉字 = 1 字符）。这个上限不是风格选择，是 GitHub About 输入框的硬约束——超过 350 贴不进去。**不设下限**：小项目机制少，229 字符写完就是好 Description（对照 `Description4.md`）
- **英文版不设字数限制**：英文版不会贴进 About 输入框，读者是点进 Description.md 来看的人，长度以信息密度为准
- 超过 350 的中文版必须重写压缩——压缩时砍冗余措辞，**不砍机制**

## 3. 内容结构（3-4 句，必含"含金量"段）

| # | 维度 | 写法 | 案例（取自 `samples/Description/`） |
|---|---|---|---|
| 1 | 是什么 + 解决什么 | 一句话定义：`<项目名> 是一个 <类型>，<解决什么问题 / 解决方式>` | "格物是一个基于 LangGraph 构建的开箱即用的多 Agent 深度研究系统，输入研究问题即可从需求澄清、研究简报、并行搜索、发现压缩到带引用 Markdown 报告的全流程自动化能力" |
| 2 | **含金量（核心，不可省）** | 列出值得写的具体技术机制（黄金样例为 4-6 个，不设硬性数量，宁精勿滥）——编排亮点 / 稳定性设计 / 工程约束 / 自研组件。**每个机制名后应跟一句它解决的问题或增效**（简历思维：HR 想看的不是"用了什么技术"，而是"用什么技术解决了什么问题"）。若机制名本身已自含效果（如"自动关单"、"防语义断裂"），可不再重复解释 | "字符分块按行边界对齐防语义断裂、SSE 四阶段流式让检索拼词生成持久化全程可见"（Code-Probe，机制自带效果尾巴）；"Lua 令牌桶限流、Caffeine 多级缓存、责任链校验、布隆过滤器、分库分表与数据加密、RocketMQ 延迟消息自动关单"（12306，机制名清单密集排列） |
| 3 | 技术栈 + 工程构成 | 不只说"基于 X 构建"，要列**具体脚本/模块/语言组合/工具生态** | "工程由 extract_skeleton.py、fetch_sources.py、bigfile_split.py 三个 Python 脚本构成，约束 git 只读、缓存落盘 skill 目录、源码不出本机，兼容 Java、Python、JS、TS、Go" |
| 4 | 目标用户 + 适用场景 | 谁用 / 什么场景用，**可与句 3 融合**为一句 | "适合快速搭建或二次工程化研究型 Agent" |

**结构灵活**：3 句长句或 4 句短句均可，关键是 4 个维度都覆盖到（维度 3、4 可融合到一句）。死板凑"4 句话"反而会稀释信号密度。**句式不必统一**——含金量段的呈现方式因项目而异：可以显式点出（"核心亮点包括…"），也可以直接铺机制清单（对照 `Description4.md`），哪种信息密度高用哪种。

## 4. 文件格式

```markdown
# Description

## 中文版

<≤ 350 字符中文描述，纯文本无 markdown 语法>

## English

<English description, no length limit, plain text no markdown>
```

输出到**目标项目根目录** `Description.md`。

外层 `# Description` / `## 中文版` / `## English` 是文件结构标记，**描述正文必须是纯文本**——不用 `**`、`[]()`、`` ` `` 等语法（GitHub About 字段不渲染 markdown，正文里出现 markdown 语法会被当原文显示）。

## 5. 风格要求

1. **描述正文纯文本无 markdown**：外层章节标题有 markdown，但描述内容里不用 `**`、`[]()`、`` ` `` 等
2. **必须有含金量段，且机制要带效果**：列出具体技术机制，每个机制名后应跟一句它解决的问题或增效（如"Token 超限自动截断重试"、"git 只读约束、源码不出本机"、"字符分块按行边界对齐防语义断裂"），不能只说"是一个 X 系统，能做 Y"。这是简历思维：读者要的是"用什么技术解决了什么问题"，不是技术名词清单。**含金量是 Description 区别于"标签"的关键**——读者看完含金量段应立刻知道这个项目的工程严格度 / 编排复杂度 / 稳定性设计的水平，而不是觉得这是个滥竽充数的项目
3. **中英版不对等**：不是逐句翻译。英文版可用主动语态 + 形象化隐喻（如 "turns X into Y"），可省略中文版的次要细节，保持同等信息密度但不必字字对应。中文版偏陈述铺陈，英文版偏主动凝练
4. **术语保留英文原文**：中文版里框架名/协议名/组件名不翻译（`LangGraph`、`Supervisor`、`Supabase`、`React`、`MCP`、`Vite`）
5. **不展开实现细节**：Description 是名片不是教程，"怎么实现的"交给 ZHIDAO.md；但**机制名**（如"Supervisor 子图"、"Token 重试"、"三层状态隔离"）可点出，不展开原理
6. **一句话能说清的不用两句**：信息密度优先于语法完整

## 6. 数据来源与提取流程

**提取流程（先列后挑，不可跳过）**：生成 Description 前，先从源码 / ZHIDAO.md 提取 **5-8 个候选机制**，逐一注明每个机制"解决了什么问题 / 带来什么增效"，再从中挑选最值得写的写入含金量段。跳过这一步直接写，是"标签堆砌"和"编造机制"两个病根的源头。

各维度的数据来源：

- **项目名 / 类型**：从 `extract_skeleton.py` 的 `project_root` + 构建标志文件推断
- **核心功能**：从 skeleton.json 的 `modules` + 入度最高的文件推断
- **含金量段（必填，最重要）**：从 ZHIDAO.md（若已生成）的"机制亮点 / 关键设计"章节，或 skeleton.json 的 `dependency_links` / 出入度高的文件提炼——必须是**源码里真实存在的机制**，不可凭空编造，且每个机制必须能回答"它解决了什么问题"。若 ZHIDAO.md 未生成，必须先扫一遍核心源码（用 `fetch_sources.py` 捞出入度最高的 3-5 个文件）确认机制存在
- **技术栈 + 工程构成**：从 `language_hint` + 构建标志文件 + imports + 关键脚本/模块名推断。脚本名/模块名要列具体的（如 `extract_skeleton.py`），不要只说"基于 Python"
- **目标场景**：从 ZHIDAO.md（若已生成）的"推荐阅读路径"或 README 推断

## 7. 已有 Description.md 的处理

- **绝不覆盖**已有 Description.md（除非用户明确要求重写）
- 用户要"更新"时保留原文，只更新过时信息
- 用户没提 Description 就不动

## 8. 正反例速查（按项目类型对照 `samples/Description/`）

生成前先判断目标项目属于哪种类型，再对照对应样例把握风格。四个样例覆盖四种含金量形态，句式各不相同——这正是要点：**句式跟着项目走，没有万能公式**。

### 高并发业务型 → `Description1.md`（12306 购票系统）——含金量在机制清单密度

> ...核心亮点包括 **Lua 令牌桶限流、Caffeine 多级缓存、责任链校验、布隆过滤器、分库分表与数据加密、RocketMQ 延迟消息自动关单**。基于 Java 17、Spring Boot 3、Spring Cloud Alibaba、RocketMQ、ShardingSphere、Redis 与 MySQL 构建，**并配套十余个自研中间件 Starter**...

✅ 六个机制名密集排列，每个都自含效果（限流/缓存/校验/过滤/关单）——业务型项目的含金量就是"高并发难题逐个有对应方案"。
✅ "单体聚合与微服务双架构形态"一句点出架构卖点，比泛泛说"支持微服务"信号强得多。
✅ 英文版不逐句翻译，主动语态凝练："registration, seat queries, flash purchase, orders, payment and refunds"一句说清业务闭环，"Every hotspot has a named countermeasure"一句统领含金量段。

### Agent 编排型 → `Description2.md`（格物）——含金量在编排与稳定性

> ...主管 Supervisor 子图拆解调度、多个研究员 Supervisor 子图并行搜索，**Token 超限自动截断重试**与异步并行检索、**结构化输出自动重试**、三层状态隔离与平台级 Supabase 认证鉴权...

✅ 每个机制都指向一个稳定性问题：Token 超限 → 自动截断重试，结构化输出失败 → 自动重试——机制与问题成对出现，信号密度极高。
✅ 英文版用形象化隐喻："turns a question into a cited report"——一句说清输入输出价值。

### 工程约束型 → `Description3.md`（Code Explain Expert）——含金量在工程约束

> ...是一套以客户项目零污染为最高原则的 AI 代码解读流水线...**它通过写入前确认护栏、骨架提取、宏观导航、可选 README/Description 与精准注释五阶段工作**，所有注释均为非破坏性追加，写入前必先告知待改清单并等待确认。**工程由 extract_skeleton.py、fetch_sources.py、bigfile_split.py 三个 Python 脚本构成，约束 git 只读、缓存落盘 skill 目录、源码不出本机**...

✅ 含金量具体到"五阶段"、"三个脚本名"、"git 只读约束"——读者立刻知道工程严格度。
✅ 约束类项目（安全、审计、只读工具）的含金量往往不是功能而是**承诺**："绝不覆盖"、"不出本机"这类承诺本身就是机制。

### 小而美工具型 → `Description4.md`（Code-Probe）——含金量在机制自带效果尾巴

> ...其含金量在 RAG 工程化：**字符分块按行边界对齐防语义断裂、SSE 四阶段流式让检索拼词生成持久化全程可见、Embedding 客户端 key 回退 LLM 配置、BackgroundTasks 后台索引加状态轮询**。JSON 文件持久化无独立数据库...

✅ 含金量段的教科书形态——每个机制 = 手段 + 效果："按行边界对齐"是手段，"防语义断裂"是效果；"SSE 四阶段流式"是手段，"全程可见"是效果。
✅ 中文 229 字符，远低于 350 上限——小项目机制列完就停，不为凑字注水，这正是字数不设下限的原因。
✅ "JSON 文件持久化无独立数据库"连短板都如实点出并转化为定位（"适合作为 RAG 工程化样本"）——诚实也是含金量。

### 反例（标签堆砌，不可写）

> Code Explain Expert 是一个 AI 代码解读工具，能帮助开发者理解项目，基于 Python 构建，适合所有开发者使用。

❌ 没有含金量段，"AI 代码解读工具"是标签不是机制。
❌ "基于 Python 构建"过于泛泛（没列脚本名）。
❌ "适合所有开发者"过于宽泛（没说具体场景）。
❌ 4 句话结构齐备但信号密度为零——正好踩中"为凑 4 句而稀释"的坑。这种输出给人的第一印象就是滥竽充数的垃圾项目：明明源码里的设计思路巧妙、解决方案厉害，简介却把它们全部抹平了。

## 9. 质量验收

- [ ] 中文版 ≤ 350 字符（GitHub About 硬约束；无下限，机制写完即止）
- [ ] 英文版无字数限制，但保持名片定位（不写成迷你 README）
- [ ] **含金量段存在**：具体技术机制非泛泛标签，**每个机制附带它解决的问题或增效**（机制名自含效果的可省略）
- [ ] 含金量机制在源码 / ZHIDAO.md 中可追溯（不编造），且经过"先列 5-8 个候选再挑选"的提取流程
- [ ] 4 个维度齐备（是什么 / 含金量 / 技术栈+工程构成 / 目标场景），可融合到 3-4 句
- [ ] 句式与项目匹配，非套公式（对照 §8 同类型样例）
- [ ] 描述正文纯文本无 markdown 语法（外层章节标题除外）
- [ ] 中英双版不对等（英文版可更精炼或更展开，非逐句翻译）
- [ ] 已有 Description.md 未被覆盖（除非用户要求重写）
