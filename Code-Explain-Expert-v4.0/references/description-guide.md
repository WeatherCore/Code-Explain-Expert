# Description 写作规范——唯一权威

> 生成项目 Description 时**只读本文件**。Description 是"项目名片"（给列表展示 / 搜索结果 / 卡片预览用），比 README 更短更精炼。

## 1. 三个产物的定位区别（必须分清）

| 维度 | Description.md | README.md | ZHIDAO.md |
|---|---|---|---|
| 读者 | 列表浏览者 / 搜索者 | 项目访客 | 要通读源码的开发者 |
| 篇幅 | **300-350 字符**（中英各一版） | 50-150 行 | 300-800 行 |
| 深度 | 是什么 + 技术栈（3-5 句） | 是什么 + 怎么用 | 为什么 + 机制 + 逐文件导读 |
| 场景 | GitHub About / 卡片预览 / 简历项目描述 / 搜索摘要 | GitHub 首页 / 项目门面 | 开发者通读代码 |
| 格式 | 纯文本（无 markdown） | Markdown | Markdown |

## 2. 字符数约束（硬性）

- **每版 300-350 字符**（含标点空格，不含换行）
- 中文版按中文字符计（1 个汉字 = 1 字符）
- 英文版按 ASCII 字符计
- **低于 300 或超过 350 必须重写**——这个区间是为 GitHub About 字段限制（350）设计的

## 3. 内容结构（每版 4 句话）

| # | 句子 | 内容 |
|---|---|---|
| 1 | 项目是什么 | 一句话定义：`<项目名> 是一个 <类型>，<解决什么问题>` |
| 2 | 核心功能 | 1-2 条最关键能力（不展开，点到为止） |
| 3 | 技术栈 | 主要框架/语言（`基于 <框架> 构建`） |
| 4 | 目标场景 | 谁用 / 什么场景用 |

## 4. 文件格式

```markdown
# Description

## 中文版

<300-350 字符中文描述，纯文本无 markdown 语法>

## English

<300-350 characters English description, plain text no markdown>
```

输出到**目标项目根目录** `Description.md`。

## 5. 风格要求

1. **纯文本无 markdown**：描述内容里不用 `**`、`[]()`、`` ` `` 等语法（GitHub About 字段不渲染 markdown）
2. **中英双版独立**：不是逐句翻译，而是各自符合语言习惯（中文版偏简洁陈述，英文版偏主动语态）
3. **不展开实现细节**：Description 是名片不是教程，"怎么实现的"交给 ZHIDAO.md
4. **术语保留英文原文**：中文版里框架名/协议名不翻译（`LangGraph`、`REST API`）
5. **一句话能说清的不用两句**：信息密度优先于语法完整

## 6. 数据来源

- **项目名 / 类型**：从 `extract_skeleton.py` 的 `project_root` + 构建标志文件推断
- **核心功能**：从 skeleton.json 的 `modules` + 入度最高的文件推断
- **技术栈**：从 `language_hint` + 构建标志文件 + imports 推断
- **目标场景**：从 ZHIDAO.md（若已生成）的"推荐阅读路径"或 README 推断

## 7. 已有 Description.md 的处理

- **绝不覆盖**已有 Description.md（除非用户明确要求重写）
- 用户要"更新"时保留原文，只更新过时信息
- 用户没提 Description 就不动

## 8. 质量验收

- [ ] 中文版 300-350 字符
- [ ] 英文版 300-350 characters
- [ ] 4 句话结构齐备（是什么 / 功能 / 技术栈 / 场景）
- [ ] 纯文本无 markdown 语法
- [ ] 中英双版各自符合语言习惯（非逐句翻译）
- [ ] 已有 Description.md 未被覆盖（除非用户要求重写）
